# Opt-in LAN room provider foundation

`createLanHostProvider` is the main-process adapter for the experimental opt-in remote room. Constructing it alone neither opens the guest authority nor listens on the network; the host must explicitly open a room. The app has no internet relay. The room is not production-ready or a promise that singers can connect.

Only trusted main-process code may construct the provider. It supplies the existing `Store`, the settings getter, a synchronous callback that installs each committed guest update into host state, a native file-picker callback, and the prebuilt allowlisted singer static handler. The provider exposes opaque handles and basenames for picker results; selected certificate and private-key paths and bytes stay in the main process. The UI must never supply executable paths, key contents, or arbitrary file paths to the adapter.

An explicit open selects a currently available private IPv4 interface, hostname, port, certificate and private key. The provider checks the hostname's DNS answers against the selected address, rechecks the interface and DNS before publication, and performs a local TLS connection using Node's configured trust roots. The HTTPS transport checks certificate validity and hostname coverage. Node and a phone browser may use different trust stores; this local probe does not establish that guest devices trust the certificate or that venue DNS and firewalls work. Public/WAN interfaces, IPv6 LAN, automatic certificate provisioning and internet connectivity are not implemented here. A trusted externally provisioned certificate and name are still required.

The provider lazily obtains the Store's one remote authority and reuses it for later rooms. It revokes credentials left from a prior host run before opening a new room. Guest registration and commands are gated until verification completes; an abort or listener error gates them synchronously, begins listener shutdown, and revokes room credentials. On a committed state-installation failure, the Store's authority fault prevents further writes until recovery. The host can enumerate at most 200 unexpired, unrevoked guests in the current show and revoke them individually; new admission stops at that bound. Room shutdown must stop the listener and revoke credentials. If either action fails, the room remains reserved and needs recovery rather than being reopened as if cleanup succeeded.

The lifecycle's abort signal stays attached throughout opening and while the room is active. A cancelled DNS or trust check cannot enable late guest access, and a listener returned after an early failure must still be closed. Successful missing-song submissions notify the host to refresh its saved request list; guest identity continues to come from the authenticated session. The provider does not give singers host controls.

Focused tests use injected file picking, private interface enumeration, trust and transport adapters, and a real in-memory SQLite Store. They cover open/close/reopen and credential revocation, guest enumeration, selection validation, delayed listener failure, trust failure, missing-song notifications and aborts during opening and an active room. An isolated Electron and Chromium rehearsal redirects its test interface to loopback and exercises the connected host and singer flows. These tests do not prove actual browser trust, physical LAN behavior, Windows firewall behavior, cross-platform packaging, DNS stability or internet access. Continue integration review and real Windows, iOS and Android tests; decide certificate provisioning and renewal. Internet access requires a separately designed and authenticated relay with its own abuse, privacy and failure testing.

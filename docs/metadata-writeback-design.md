# MP4 metadata write-back design

**Status: planned, not implemented.** Editing a song today changes the local library only. The host must get a per-edit choice to also update Artist and Title inside a supported MP4; that choice starts unchecked. The app must clearly report whether the library and the source file were each updated. A failure or unsupported file must never be presented as a successful file write. Do not silently opt future edits into file modification.

## Candidate writer

Investigate a pinned, licensed, app-distributed metadata writer rather than assuming an executable exists on `PATH`. ExifTool is a candidate because it can write explicitly selected MP4 `ItemList:Artist` and `ItemList:Title` to a separate output file. [ExifTool documents QuickTime metadata groups](https://exiftool.org/TagNames/QuickTime.html) and its [original-file preservation and output options](https://exiftool.org/exiftool_pod2.html). MP4 files can contain conflicting Artist or Title values in multiple groups; define which groups are read and written and show conflicts instead of silently deleting unrelated metadata. Verify what other applications display.

An isolated test on one synthetic MP4 wrote the two ItemList tags to a separate file using the locally installed ExifTool; the source remained present and the audio/video stream hashes matched. This is feasibility evidence only, not a guarantee for other MP4 variants, codecs, embedded tags, or file systems. FFmpeg stream copy is not a sufficient preservation guarantee for MP4 metadata; [FFmpeg's mailing list documents an example of metadata changing during a copy](https://ffmpeg.org/pipermail/ffmpeg-user/2020-January/046434.html). Do not adopt remuxing without preservation testing for all supported structures.

The writer must run without a shell, accept only host-selected library entries, and never accept a renderer-provided executable or output path. Validate text and all options, reject NULs, impose reasonable resource and time bounds, and handle failures and cancellation. Test Windows Unicode metadata and paths, newlines, long names, quotes and leading dashes; [ExifTool's Windows filename guidance](https://exiftool.org/faq.html#Q18) describes encoding constraints. If an argument file is used, user-provided newlines must not become additional tool options. Check distribution licensing, packaging, upgrades and code-signing; unsupported writer or platform means file write is unavailable, with local editing still available.

## Proposed operation and recovery

The current `media.fingerprint` is a SHA-256 of the entire imported file. Even a metadata-only file change alters it. Leaving the old fingerprint would break duplicate detection and source-change checks. No SQLite transaction can atomically commit a file replacement, so implement and test a durable journal and reconciliation protocol before enabling the checkbox.

1. On the main-process authority, validate the host's desired local metadata and explicitly requested file write. Serialize writes for the song, and refuse or defer changes to a currently playing source. Identify a regular, supported local MP4 without following an unexpected link. Check source identity, accessibility, full-file hash and file-system capabilities; if the file changed since import or is concurrently modified, stop and offer review rather than overwrite it.
2. Retain a uniquely named, independently verified original backup and record its identity and original hash in a durable operation journal. Generate a uniquely named output on the same volume without changing the original. Avoid collisions and never overwrite another file. Confirm the tool exited successfully, re-read the requested tags, re-hash the output, and verify that required streams and unrelated metadata are preserved within the declared support envelope. Validate Unicode and empty values. If verification fails, keep the original untouched, report the failure, and leave recoverable artifacts where needed.
3. Before replacement, persist the pending operation with original, replacement and backup identities and hashes. Recheck source identity and hash. Use a platform-specific replacement primitive with an original backup, rather than assuming a rename on every file system provides equivalent guarantees. On Windows, evaluate [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), including its documented partial-failure states, same-volume requirement and attribute behavior. Cloud-synced folders, network shares, hard links, reparse points, access-control entries, and a competing external writer need special handling; decline the file write when the required guarantees cannot be established. A hash recheck alone cannot eliminate a concurrent-writer race.
4. After a verified replacement, persist the new library metadata and new media fingerprint together in the authority's SQLite transaction, then mark the journal complete. If the host chooses to save the local edit despite a file-write failure, persist that local result separately and clearly label the file failure. Keep a recoverable backup according to an explicit retention and user cleanup policy; do not delete originals or backups automatically during uncertain recovery.
5. On restart, inspect incomplete journal records before permitting edits to affected entries. Reconcile known original and replacement hashes with the file, backup and database. If the state is ambiguous, prevent further writes and give the host clear recovery choices; never overwrite a file whose identity or contents differ from the journal. Test interruption at every transition and make operations idempotent. Be explicit about what durability the platform and file system actually provide.

## Remaining work and acceptance checks

- Choose and package a writer, define per-format/tag-group support, verify licensing, and implement host-facing choice and result/error states.
- Implement the main-process write coordinator, durable operation journal, same-volume backup/replacement adapter and recovery flow. Preserve the single show authority and update the library fingerprint and duplicate detection safely.
- Test valid and unsupported containers, non-ASCII values and paths, long and empty tags, existing conflicting metadata, multiple audio/video/subtitle/data streams, artwork and unknown boxes, malicious metadata, permission errors, insufficient space, active playback, external changes, process termination, and interrupted replacement or database transactions.
- Test physical Windows files and Dropbox-synced files as well as any other supported platform. Verify playback, media data and unrelated tags before and after, backup usability and recovery. Do not enable writes for a storage provider or file system solely because a synthetic local-file test passed.
- Update host help and developer documentation to explain the per-edit choice, file backup, supported formats, potential conflict handling and recovery; singer-facing documentation should describe only behavior relevant to singers.

# Mobile store data inventory — draft

Reviewed 20 November 2026 against the repository for the proposed Android and iOS app. This is an engineering inventory, not a completed privacy policy, store declaration, legal conclusion, or confirmation of the deployed server configuration. Recheck the exact signed release, deployment, SDKs and provider contracts before submitting. The host and guest may be different people; do not treat a host's choice as every guest's consent.

## Data flows and retention

| Data / action | Flow and intended storage visible in this code | Evidence and unknowns |
| --- | --- | --- |
| Mobile host show | Show name, singers' display names, songs, requests and status, favorites, history, missing-song requests, points/credits, settings and playback position persist in on-device IndexedDB. Recovery copies can persist an earlier show. | [`src/mobile/show.ts`](../src/mobile/show.ts), [`src/mobile/storage.ts`](../src/mobile/storage.ts). Browser/OS backup and deletion behavior varies. No server-side show-account sync is established. |
| Local video | User-selected video blobs are copied into on-device IndexedDB and played locally. The host can remove a device copy while retaining metadata/history; the original file is untouched. | [`src/mobile/storage.ts`](../src/mobile/storage.ts), [`src/mobile/App.tsx`](../src/mobile/App.tsx). Verify actual native file-picker and OS-backup behavior. |
| Guest identity and queue | A chosen display name and generated session identifiers travel to the host when joining and making requests; the host receives song requests, availability, suggestions and applause. The guest client keeps its admission/session/resume secrets in memory. | [`src/remote/client.ts`](../src/remote/client.ts), [`src/remote/internet-transport.ts`](../src/remote/internet-transport.ts). Mobile-host guest/session maps are in memory, while names and show activity can enter the host's persisted show. Desktop hosts persist show state and guest/session records, including hashed secrets and join name, in their local SQLite database ([`src/main/remote-queue.ts`](../src/main/remote-queue.ts)). Host backups and retention/deletion require separate review. |
| Search | Mobile searches and terms are sent over HTTPS to the queue service; its mobile catalog adapter queries the local shared catalog service. Guest searches are sent to the selected host through the room relay. | [`src/mobile/App.tsx`](../src/mobile/App.tsx), [`src/mobile/api.ts`](../src/mobile/api.ts), [`src/relay/mobile-catalog.ts`](../src/relay/mobile-catalog.ts). Reverse-proxy, catalog, security and provider logs/retention must be verified in the actual deployment. |
| Room discovery | With discovery enabled, native devices can advertise a room name and public room link over local DNS-SD. The same-egress fallback sends network requests to the relay; its implementation computes a keyed hash of the observed IP and keeps short-lived entries in memory. Hints are not proof of proximity. | [`src/mobile/discovery.ts`](../src/mobile/discovery.ts), [`src/relay/mobile-access.ts`](../src/relay/mobile-access.ts), [`mobile/ios/App/App/Info.plist`](../mobile/ios/App/App/Info.plist), [`mobile/android/app/src/main/AndroidManifest.xml`](../mobile/android/app/src/main/AndroidManifest.xml). Networks, Cloudflare and hosting infrastructure can still see network metadata; verify actual logs and retention. |
| Photos | A singer explicitly selects a JPEG/PNG. The browser decodes and re-encodes it before sending to the host; images can contain identifying visual content despite removal of file metadata. Relay requests are held in memory while delivered; the mobile host displays the image temporarily and keeps a receipt/hash, not the image, in the show state. | [`src/remote/photo.ts`](../src/remote/photo.ts), [`src/relay/broker.ts`](../src/relay/broker.ts), [`src/mobile/room-authority.ts`](../src/mobile/room-authority.ts), [`src/mobile/App.tsx`](../src/mobile/App.tsx). Desktop sends to its display callback without photo bytes in receipts ([`src/main/remote-queue.ts`](../src/main/remote-queue.ts)). Do not assume a third party, server log, crash dump or host cannot retain a copy. |
| YouTube playback | Online playback uses YouTube's player/iframe and requests to YouTube domains; those services can receive network/device and playback information under their own practices. | [`src/mobile/Player.tsx`](../src/mobile/Player.tsx), [`mobile/web-public/youtube-player.js`](../mobile/web-public/youtube-player.js), [`deploy/queue-relay/mobile.conf`](../deploy/queue-relay/mobile.conf). Review actual YouTube data practices, terms and embedded player behavior before declaring data use. |
| Relay operations | Room slug, random room/generation IDs, owner ID and lease expiry may be stored in the relay database; request envelopes and photos are handled in memory during delivery. A short-lived mobile-host capability and same-egress indexes are held in memory by the shown implementation. | [`src/relay/store.ts`](../src/relay/store.ts), [`src/relay/mysql-store.ts`](../src/relay/mysql-store.ts), [`src/relay/broker.ts`](../src/relay/broker.ts), [`src/relay/mobile-access.ts`](../src/relay/mobile-access.ts). The sample Apache log format excludes URL/IP, but deployment, error logs, backups, Cloudflare and retention are not verified here ([`deploy/queue-relay/apache-queue.conf`](../deploy/queue-relay/apache-queue.conf)). |

The source manifest requests Android Internet permission and iOS declares local-network usage and Bonjour discovery. This is **not** a complete merged Android manifest, iOS privacy-manifest/required-reason audit, runtime permission check, or inventory of all transitive SDK behavior. The reviewed mobile source does not establish paid KaraFun/Party Tyme playback, a mobile account system, advertising, analytics or crash reporting; verify the final bundle and third-party services before making a negative claim.

## Release and review gates

- Publish a real, accessible privacy policy and in-app access to it; specify purposes, recipients, retention, deletion/contact process and third-party practices. Reconcile the signed binaries, deployed configuration and actual logging/backups with the policy. The current inventory alone is not a user-facing policy.
- Complete Apple App Privacy and Google Play Data safety from the final implementation, including integrated third-party code. Their definitions of collection differ: Apple describes certain real-time handling separately; Google requires ephemeral off-device processing to be included in the form even where it may not appear publicly. Do not assume all transferred photo/room data is exempt. [Apple App Privacy details](https://developer.apple.com/app-store/app-privacy-details/); [Google Data safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en).
- User-submitted photos and room names/requests need a moderation review. The shown photo path displays a submitted image rather than providing a pre-display content filter; no general in-app report/abuse workflow was found in the inspected mobile/singer screens. Desktop guest revocation exists, but is not equivalent to a complete platform-wide blocking and reporting process. Determine applicability and implement appropriate safeguards, contact and response procedures. [Apple guideline 1.2](https://developer.apple.com/app-store/review/guidelines/); [Google developer policies](https://support.google.com/googleplay/android-developer/answer/18265346?hl=en).
- Define and test deletion/export and retention for local shows, recovery copies, media, desktop-host guest data, relay/database backups and logs. Existing mobile **Remove Device Copy** deletes a selected video copy while keeping its metadata and history; it is not a complete personal-data deletion feature. The evidence above does not establish a general deletion workflow.
- Verify rights and platform/provider terms for each shipped catalog, trademark, streamed video and commercial use. Apple asks for authorization where third-party content is streamed or downloaded. Do not represent a personal subscription as partner authorization. [Apple App Review preparation](https://developer.apple.com/app-store/review/).
- Audit Xcode privacy manifests/required-reason APIs, third-party dependencies, permissions and final signed packages; test local-network discovery, background/restore, playback and accessibility on real Android and iOS devices. Prepare truthful reviewer access and screenshots.
- Confirm developer-account identity, signing and store access. If the Google account is a **personal** account created after 13 November 2023, Google currently requires a closed test with 12 opted-in testers for 14 continuous days before applying for production access; other account types or creation dates may differ. [Google testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en).

# Remote queue boundary prototype

`src/main/remote-queue.ts` is an unconnected, transport-independent authority prototype. The intended product supports singers joining from both the venue's local network and the internet. The prototype does not open a port, provide a guest website, validate HTTPS, or implement an internet relay. Neither LAN nor internet remote queueing is usable until those pieces are built and independently tested. Do not expose this class directly as a generic RPC object.

## Integration

Instantiate it in the Electron main process against the same `DatabaseSync` connection and `show_state` row as `Store`. Supply a synchronous settings getter and an `onCommitted` callback that **first replaces the host's in-memory show state**, then publishes it to the renderers. All show mutations, including the existing host path, must stay serialized on that one authority; never give a transport process direct database write access. The callback must not throw. If a callback can fail before installing the state, fail closed and restart/reload before accepting any other command. Guest writes commit the show and their receipt in the same SQLite transaction, then invoke this callback before returning.

Host-only methods `createInvitation`, `revokeGuest`, `revokeInvitations`, and `closeRoom` must never be exposed to unauthenticated or guest routes. A trusted HTTPS endpoint may exchange a short-lived high-entropy admission token for `join`. An invitation can admit multiple guests until it expires or is revoked; revoking invitations prevents new joins but does not revoke guests already admitted. Browser code must generate a new 32-byte resume secret with a cryptographic random generator and keep it private. The returned session is a separate 32-byte random bearer credential. Hashes only are stored. Session lifetimes are eight hours; resume credentials expire after 24 hours, and both can be revoked by closing the room. A newly constructed service has a new run ID, invalidating prior sessions; a guest can reauthenticate with its resume secret to recover its earlier command outcome. Protect credentials from logs, analytics and referrers. Do not put session or resume secrets in URLs; if an invitation is shared in a URL fragment, erase the fragment from the browser history after reading it.

Derive guest actor and singer solely from the authenticated session. `submit` accepts only a song version ID, caller-supplied command ID, show/epoch and expected revision; it rejects additional fields, including role and singer ID. Retries with the same command and same guest return the persisted outcome even after a new host epoch; changed content returns `COMMAND_ID_REUSED`. Use `outcome` after an uncertain response, and do not automatically replay stale controls. `snapshot`, `catalog`, and `catalogItem` all apply the show policy and only return selected guest-facing fields; `catalog` is bounded and revision-tagged.

Before enabling a listener, implement explicit host opt-in, authenticated TLS with trusted certificates and hostname verification, same-origin Host/Origin and CSRF checks, authorization at every route, request/body/rate/connection limits, secure cookie handling and revocation, input/output schemas and structured errors. For an internet relay, use separately designed end-to-end authentication, scoped credentials, transport reconnection and a hosted deployment; a LAN listener alone does not provide internet access. Do not silently fall back to plain HTTP or ask guests to bypass TLS warnings.

The guest page, host enable/disable and invitation controls, service lifecycle, route adapters, discovery and trusted certificate provisioning, relay deployment and availability behavior still need to be implemented. Any route adapter must enforce bounded request and response schemas and establish the documented security controls before this prototype is reachable. The host authority integration must handle committed-but-unpublished state without accepting subsequent mutations against stale in-memory data. Local and internet modes must use the same authority and policies, and a relay outage must not prevent an already running local show from continuing.

The test suite exercises authorization isolation, expiry/revocation, policy filtering, admission retries, concurrency via revision conflicts, durable replay across a new service run and host epoch, and a forced transaction failure. It does not test network, browser, relay, certificate or real-device behavior.

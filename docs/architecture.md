# Architecture and progress

Updated 12 November 2026 for development version 0.4.0. This describes implemented source and recorded rehearsals; future engine and platform choices remain open.

## Current show authority

The Electron main process owns the local show. The host UI and singer display are isolated renderers with narrow preload bridges. The host sends validated commands to pure show rules; SQLite commits show changes and private media locations before the caller is notified. The singer window owns queued karaoke playback and experimental bumper audio. It reports its clock and completion with a playback generation; preparing a staged request does not start audio. The separately opened YouTube preview is outside the show queue, and an audio gate prevents it from overlapping karaoke or bumper playback. The native media element remains a replaceable experimental engine.

State is stored as a serialized show in local SQLite, with media locations and playback checkpoints in private tables. SQLite uses WAL and synchronous FULL. A new host epoch is issued on restart, and an interrupted performance is restored paused. Domain commands use expected revisions and persisted receipts. Local browser and internet singer commands additionally use authenticated identity, durable command receipts and explicit outcome checks/retries after uncertain responses. Neither the relay nor CLI opens a second writer to the host show database.

The host renderer gets no arbitrary filesystem or generic IPC access. Imports go through native file pickers, SHA-256 fingerprints are stored, and video is delivered through a generation-scoped local protocol. File identity is checked on verified open handles for media ranges; an observed replacement pauses the affected performance rather than advancing the queue. That does not make arbitrary concurrent in-place source writes safe. Trusted file operations, download processes and network credentials stay in the main process. The manually started external YouTube preview is separately constrained; remote content is not loaded into the privileged host renderer.

Metadata corrections currently update the local library only; embedded tag reading and write-back are not yet implemented. Product direction is a per-edit choice: local-only by default, or explicitly request writing supported embedded tags as well. A failed or unsupported file update must be reported without discarding the local correction. Import, rescan, and ordinary edits must never implicitly modify source media. See the [write-back plan](metadata-writeback-plan.md) for the preservation and concurrency requirements.

New requests default to automatic approval, with optional moderation. This supersedes the original handoff's moderated-by-default direction. A setting change affects new requests rather than silently approving pending ones. FIFO and singer-round choices operate on the same durable queue; staged requests remain locked. Manual order, waiting-request edits and timed absence operate through that authority without changing an active performance implicitly.

## Remote access and local control

The experimental LAN singer service requires a separately opened room, private-network hostname and trusted HTTPS setup. Internet Remote Sessions use the deployed HTTPS relay at `queue.thepropervolume.com`, backed by isolated MySQL on Linode. An outbound host connector delegates commands to the same local show authority. Local rooms and internet sessions have separate access scopes. Public packaged-host/browser request and lost-response recovery rehearsals passed; self-service account provisioning, physical phones, venue-network reliability and long-show verification remain unfinished. See [relay integration](internet-relay-integration-plan.md).

The authenticated local control API is independent of the singer services and disabled by default. Explicitly enabling it starts a loopback listener with an owner-only per-start credential. It exposes capabilities, bounded state/settings/shortcut reads and queued Preferences/Keyboard Shortcuts navigation. The compiled CLI uses that authority and reports supported capabilities; playback, queue, import and other mutation endpoints are not implemented. Disable/quit closes the listener and removes its own discovery file; restart rotates the credential. The desktop launcher also supports settings/help navigation independently of the API. See [local API and CLI](local-control-api.md) for implemented routes, security constraints and exit codes.

## Shared catalog and ratings

The dedicated MySQL catalog service at `apps.thepropervolume.com` is deployed and connected to Song Library discovery. It serves 64,261 valid unique YouTube recordings from the recovered Karaoke Nerds snapshot. Fresh installations use bounded public read-only search without a credential file. Optional private profiles use separately scoped reader credentials and caches; an invalid selected profile is reported rather than silently bypassed. Previously successful queries can be retained for labeled offline reuse. Upstream freshness is unknown and automatic refresh is disabled until updater retirement and refresh history are established. The host show database remains local SQLite; database and upstream provider credentials stay server-side. See [catalog operations](karaokenerds-catalog.md).

Karaoke Nerds supplies recording metadata and YouTube links, not a paid playback entitlement. Accepted catalog requests dispatch permanent acquisition through yt-dlp; completed media attaches to the existing version and uses the ordinary local queue/player without autoplay. FFmpeg and yt-dlp are host prerequisites. Automatic brand/artist batch downloads remain planned.

Shared recording-quality heart ratings use a separate MySQL schema and authenticated service. Public readers receive aggregates; a provisioned host voter credential permits one replaceable vote per exact recording. Catalog reader access cannot write ratings. Credentials stay in the main process, and verified singer accounts or remote self-service voting are not implied. No paid karaoke provider is connected for playback or existing-subscription sign-in. Provider SDK/API access and rights remain separate prerequisites.

## Media investigation and verification

**Historical investigation, 6 November 2026:** the original Linux laptop reported FFmpeg CDG decoding, H.264/AAC/MP3 codecs, rubberband/atempo and fades, plus mpv 0.37, GStreamer and PipeWire. The initial muted Electron rehearsal used a generated 20-second H.264/AAC fixture and checked dimensions and advancing time. These are dated observations about that environment, not current dependency requirements or evidence of audible output.

**0.4.0 verification:** actual Windows source-app and compiled CLI rehearsals passed, followed by packaged Windows runtime, bundled-wrapper/API lifecycle, settings-launch, CDG backdrop and persistence checks. Linux 0.4.0 package/runtime checks also passed in a root/Xvfb rehearsal with test-only flags; this does not verify normal-user sandbox behavior or desktop installation. macOS remains unbuilt. See [installation](installation.md) for exact artifacts and verification scope. Physical sound/mixer routing, second-monitor hot-plug, audio-device unplug, actual phones, install/upgrade/removal and long-show behavior remain verification work.

Play opens the singer display on its remembered screen when available, then the nearest non-host screen, or the current screen. The host can explicitly choose another monitor. A disconnect of any monitor previously used by that open window can conservatively pause playback, even after the window moves elsewhere. Recovery requires deliberate host action.

Evaluate real-producer CDG/audio synchronization and seek reconstruction, independent real-time pitch/tempo, output-device selection and loss, single-audio ownership, filler transitions, accessibility, and packaging/licensing on each platform before choosing a final engine. Current MP3/CDG and ZIP support converts to managed MP4 through FFmpeg; native CDG and LRC playback remain future work. MP4 is a container; codec support varies.

## Known limitations and next steps

See the [roadmap](roadmap.md) and [remaining work](remaining-work.md). Song restrictions need fuller owner controls, richer evidence and enforcement at every eventual API boundary. Current domain policy and filtered guest catalogs do not establish a complete moderation or access-control model. Indefinite singer holds, skip-turn semantics, approximate wait times, named-show management, profiles, general API mutations, billing and paid providers remain unfinished. Extend transactional, authorization, restart and concurrency coverage as each feature is added; retain one host authority and deliberate playback recovery. Passing isolated rehearsals does not establish live-show readiness.

# Connector staging foundation

`src/main/connector-staging.ts` is an unconnected, offline main-process helper. It neither downloads, installs nor executes `cloudflared`, opens a tunnel, or changes PATH. The normal app does not invoke it. The host supplies a selected executable from an official source; the default trusted digest and release are app-owned, pinned Windows amd64 data from [Cloudflare's 2026.10.7 release](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.7). The optional release parameter is for trusted main-process release data and tests, never guest or renderer input.

The trusted main-process caller must provide an already-private, app-controlled staging root; never accept that root or a release digest from a renderer. The helper rejects a linked root and verifies the existing parent's owner and restrictive ACL before creating any child. Provisioning and securing that parent is an integration prerequisite; this helper does not silently change an existing root's permissions. It inspects the selected regular file against the pinned digest, creates a unique staging directory beneath that root, restricts it, copies bytes to a newly created executable, checks the copy against the same digest, and inspects the copy again. On Windows it replaces inherited child access rules with an explicit current-user and Local System ACL, verifies the directory rules, and checks the staged file has no access rules for other accounts. On other platforms it checks owner-only mode bits. It fails closed if its platform permissions cannot be applied or verified. A launch caller must call `verifyForLaunch()` immediately before spawning; it checks the root, reapplies child restrictions, checks file access rules and rehashes the staged executable.

`withStagedConnector()` wraps a trusted callback and cleans the staging directory after the callback settles. The caller must wait for the child process to exit before settling; this helper does not supervise a process. Explicit `cleanup()` is also available and is idempotent. The root identity is rechecked after permissions checks and during launch and cleanup; cleanup also checks the child identity and resolved parent before recursive removal, refusing a substituted path. If setup or wrapper cleanup fails, a main-process-only `ConnectorStagingCleanupError` carries a retry handle; callers must preserve it rather than silently discard it. An abrupt crash or power loss can leave a directory behind, so future integration needs a bounded, identity-checked recovery procedure for stale staging directories.

The ACL and digest lower exposure to other local accounts and catch changed bytes, but they do **not** establish absolute tamper protection. The same Windows account, an administrator, or another privileged process may modify permissions, files or paths between the final check and process creation. Node's path-based spawn does not bind execution atomically to the inspected file handle. Before public integration, review Windows handle/share-mode or equivalent platform controls, binary provenance, race and crash behavior, process containment, and release-update policy. Do not claim a checksum is a signature, that ACLs block administrators, or that a pinned development version is automatically maintained.

Tests use synthetic bytes only; the Windows suite checks the real parent/directory/file ACL and cleanup, rejects permissive, linked or substituted roots and a mismatched digest, detects staged-file tampering, refuses substituted directories and exercises cleanup recovery. It has not executed a staged connector or launched a public relay.

# Karaoke Nerds community catalog groundwork

Karaoke Nerds granted access to its community metadata feed with the request that it be called about once per day and cached. A recovered raw snapshot contains **64,261 records**. The dedicated MySQL service is now deployed behind HTTPS at `https://apps.thepropervolume.com`, isolated from the website's databases. Its current search projection contains **64,261 valid, unique YouTube recordings**, including records whose brand has not been mapped to a public slug. A server catalog backup and scratch-database restore check passed. No new upstream feed request was made to establish this deployment.

**Freshness and verification limits:** the original SQLite catalog, refresh-cooldown state and verified retirement/mapping state were not recovered. The server's `lastAttempt`, `lastSuccess` and `sqlite_retired_ms` are null. Snapshot file dates are not upstream attempt times. Refresh is disabled, with no provider key or refresh gate provisioned for this service. Do not claim that old updater copies were retired or that the catalog is current. Live Windows-to-service HTTPS status and search now pass: status returns 64,261 raw/searchable records and a Nada Surf / Amateur search returns one result. A new client instance reused that query from the durable offline cache with a stale label after a simulated connection failure. Actual catalog-to-download playback and show hardware remain separate verification work.

## Desktop shared-catalog workflow

In 0.2.0, **Preferences → Shared Karaoke Nerds Catalog** can choose a private client configuration, check access and save whether searches use it. The configuration is a private JSON file with `baseUrl` and `token`; its origin is the approved HTTPS service, and its token is a scoped read-only client credential, not the Karaoke Nerds provider key or a database password. Blank configuration selection uses `catalog-connection.json` in the app data folder. A protected configuration has been provisioned for this Windows host, with a private backup under `C:\tmp`. Packages do not include it. Keep configuration copies private; never paste their token into a message, document, repository, settings JSON or renderer.

The main process validates and reads this file, makes bounded HTTPS requests without redirects and projects only public catalog fields to the host UI. Previously successful queries can be saved in a bounded offline cache (100 entries, 20 MiB) under the app data folder. Cached responses are labeled offline/stale and show when they were fetched; this is a query cache, not a complete downloadable catalog. New searches without a cached match need the server. Unauthorized/forbidden responses do not fall back to an old authorization scope's cached data. When shared access is unconfigured or explicitly disabled, the legacy local SQLite browser remains available; the default Windows local snapshot is still absent. A configured remote failure is reported rather than silently choosing another catalog.

In 0.3.0, the ordinary **Song Library** search also includes Karaoke Nerds recordings after a short typing pause. Local matches appear immediately, and catalog outages do not erase them. Saved offline results show their saved time and a stale warning; new uncached searches still need the service. Repeated results with the exact same YouTube ID appear once, with an existing library song and its edited metadata taking precedence. Different recordings of the same artist/title remain separate. Search changes cancel pending work and ignore late replies from an earlier query.

Double-click a library or catalog row, press Enter on it, or right-click **Add to Queue**, then choose or enter the singer. A catalog-only selection is added and requested through the host authority without a separate **Add to Library** step. Its permanent yt-dlp download is scheduled once the request is approved: immediately under default auto-approval, or after the host accepts it under manual moderation. The **YouTube** service badge replaces a local DJ/track code. The show policy and library filters still apply: an excluded recording cannot reappear through the catalog, and new unrated recordings are hidden under clean-only or explicit include-list policies. A successful catalog search does not mean a video has already downloaded or can start immediately. Completing a download does not start playback.

Unmapped brands remain unmapped (`brandSlug` is empty); do not invent a brand slug or directory from a raw brand code. Such videos use the ordinary YouTube cache directory. The current deployed recovery contains no verified historical brand/video mapping or producer-code state. Singers browse only the host's loaded song library; they do not receive catalog service credentials or query this central service directly. The separate **Karaoke Nerds** page remains available for manual YouTube links and previews. See [YouTube playback](youtube-streaming.md).

## Refresh hold and future cutover

Before enabling any upstream refresh, locate or reconcile every old updater and its credential, establish a conservative known last-attempt time, and provision one durable central gate that counts failed attempts and survives restart. Do not reset a cooldown or launch an independent refresher to compensate for the recovered state. Verified brand mappings, producer codes and yt-dlp dates may be imported later only from a validated source. The host show/queue database remains local SQLite and remains the sole playback authority; the shared MySQL service stores catalog metadata only.

The following SQLite export and operator controls remain migration/recovery tools. They do not establish that the current raw-snapshot recovery passed the original retirement prerequisites, and they do not authorize refresh activation.

The SQLite operator exposes `sqlite-refresh-status`, `sqlite-refresh-retire`, `sqlite-refresh-recover-stale` and `sqlite-refresh-resume`. Retirement or recovery requires `TPV_KARAOKENNERDS_CONFIRMED_STOPPED=true` only after the operator has independently stopped every old updater and isolated its key. A retirement marker blocks new refreshes on that SQLite file and makes earlier binaries reject it; already-open processes and independent copies still require operational shutdown. A stale outstanding attempt fails closed and needs explicit recovery. Resuming SQLite after a rollback also requires the stopped central updater's verified last-attempt time in `TPV_KARAOKENNERDS_CENTRAL_LAST_ATTEMPT`. Each transition establishes a fresh minimum 24-hour cooldown. The migration export refuses a database without a verified retired marker or with an outstanding attempt.

The server-side `scripts/karaokenerds-mysql.ts` supports `initialize`, `import`, `seed-readonly`, `status`, `refresh` and `recover-refresh`; it reads database and upstream credentials only from private files, accepts a local Unix socket or loopback database host, and never contacts the provider during initialize, import, status or recovery. The deployed raw recovery used `seed-readonly`, which requires `TPV_KN_REFRESH_DISABLED=yes` and a private existing snapshot in `TPV_KN_RAW_SNAPSHOT_FILE`; it deliberately leaves upstream attempt/success and retirement state unknown rather than inventing a cooldown. The separate migration `import` requires `TPV_KN_LEGACY_UPDATER_STOPPED=yes` and a validated retired SQLite export; the imported cooldown is at least the MySQL server time at import. Refresh requires `TPV_KN_SINGLE_UPDATER_CONFIRMED=yes`. An interrupted outstanding attempt returns `recovery-required`; after verifying the updater is stopped, `recover-refresh` requires `TPV_KN_CONFIRMED_UPDATER_STOPPED=yes` and establishes a new cooldown. Only the production updater may hold the actual Karaoke Nerds credential; staging uses synthetic data.

The observed feed includes artist, title, brand, watch link and a nullable `Created` value. The links observed are YouTube watch pages. `Created` is a .NET-style timestamp when present, but it does not reliably represent the linked video's publication time: an inspected example differs from the video's own metadata. The feed's brand value is an internal lookup and join key; the cache path uses the corresponding verified Karaoke Nerds brand-page slug. Do not invent a slug for an unresolved or ambiguous match, or infer publication order from the feed's `Created` field. The individual-video acquisition tool is now `yt-dlp`; a metadata credential alone does not establish rights to download or distribute media.

For a selected brand, the operator tool can request the public community directory and that brand's public page, then match exact YouTube IDs against the saved feed. It stores a mapping only when all matched feed records agree on one brand code. A historical local mapping matched 404 videos for `TheProperVolume` to `PVOL`; no additional authenticated feed request was needed. That verified mapping state was not recovered into the current shared deployment. Unknown or conflicting matches require review. The schema can retain brand codes, YouTube video IDs and nullable verified producer track codes; these fields must not be represented as recovered when they were absent from the recovery source. A producer code such as `PVOL-003` is not a YouTube ID and is not inferred from a filename or feed position.

## Host preferences and future media caching

Preferences saves a base directory, an opt-in automatic-cache preference, and optional lists of brands and artists. The base folder now controls individual host-selected downloads. Automatic brand/artist selection preferences remain preparatory: enabling them does not start a batch. The requested artist policy is the most recently published video for each artist and track. Prefer a verified publication date; when it is unavailable, use yt-dlp's upload date as the best available approximation, retaining its provenance. If competing versions lack both usable dates, report the uncertainty rather than silently guessing.

The legacy operator-only `yt-dlp` adapter can inspect metadata or download one explicitly selected YouTube video. It invokes an absolute executable without a shell, disables external configuration and plugins, verifies the downloaded MP4 header, and publishes through an exclusive hard link at the planned path. It uses separate MP4 video and M4A audio with ffmpeg when available, falling back to a pre-merged MP4; the cache directory must already exist and support hard links. One real test of the owner's video produced an H.264/AAC MP4 in a temporary directory. An operator command can choose a mapped catalog track; it is not connected to Preferences, the host catalog interface, automatic jobs or the song importer. Cancellation stops yt-dlp, but descendant ffmpeg process cleanup still needs verification and implementation. If a started process fails or is cancelled, its `.tpv-yt-` staging directory is retained; check for an active ffmpeg process before reviewing that directory or retrying. The filesystem checks reduce path-substitution risks but cannot rule out every concurrent same-user filesystem race.

The separate batch-planning prototype forms the union of selected brands and artists, reports path collisions, and refuses to select a newest artist version unless the caller establishes complete artist coverage and supplies a usable date for each competing version. Each version uses its verified publication date when available, otherwise a yt-dlp upload date whose provenance and video ID match. A ranking that compares any upload fallback is approximate even when the selected video's own date is verified; the Karaoke Nerds `Created` field and yt-dlp release date are not publication-date substitutes. An explicitly selected brand can still include its own versions. Its serial executor runs only a reviewed plan and stops at a failed or cleanup-needed item. Neither prototype is connected to automatic jobs or the host interface.

The intended layout is:

```text
$BASE_CACHED_VIDEOS_DIR/$PROVIDER/Brands/$BRAND_SLUG/$ARTIST/$ARTIST - $TRACK_NAME.$FILE_EXTENSION
```

For example, `/chosen/path/karaokenerds/Brands/TheProperVolume/Nada Surf/Nada Surf - Amateur.mp4`. The path planner sanitizes unsafe components and identifies case-insensitive or sanitized-name collisions. It does not write files; future writers must also reject symlink escapes and existing-file overwrites, validate source permissions and report per-file failures.

## Operator prototype

`src/catalog/karaokenerds.ts` stores one validated snapshot and the last attempt and success in one SQLite database. It acquires an attempt transactionally before making a request and enforces a minimum 24-hour interval between attempts under normal operation, including failures. Invalid or failed responses leave the last good snapshot intact. A new snapshot containing less than half the prior record count is also rejected for review, guarding against a truncated dump; a legitimate large catalog reduction requires operator investigation. The coordinator only protects callers sharing that same database; creating separate databases or independent clients bypasses the gate. The deployed service supplies the read-only central search boundary; upstream refresh remains disabled until the missing attempt/retirement state is reconciled. No provider key is embedded in the application.

`scripts/karaokenerds-catalog.ts` is an operator-only prototype with `seed`, `refresh`, `status`, `map-brand`, `brands`, `tracks`, `set-track-code`, `inspect-video`, `download` and `preview-batch` operations. It requires an absolute database path in `TPV_KARAOKENNERDS_DATABASE`; `seed` additionally reads an existing private response snapshot from the path in `TPV_KARAOKENNERDS_INITIAL_SNAPSHOT`, and `refresh` reads private credential material from the path in `TPV_KARAOKENNERDS_CREDENTIAL_FILE`. The latter must be accessible only to the authorized operator. Do not put credentials, raw catalogs or their private paths in Git, client builds, logs, bug reports or documentation. Keep the database private and back it up without making a second active updater.

With the repository's development dependencies installed and those environment variables set privately, use `node --import tsx scripts/karaokenerds-catalog.ts status` to see the record count and attempt times. Use the same command with `seed` to initialize an empty database from a prior snapshot, or `refresh` to request an update when due. Times are Unix milliseconds. The credential file contains the complete privately supplied endpoint URL; never pass it as a command-line argument or print it. The `seed` command establishes a fresh 24-hour cooldown from initialization, so seeding the first fetched snapshot does not immediately make a second call.

Set `TPV_KARAOKENNERDS_BRAND_SLUG` to a selected public brand slug before `map-brand` or `tracks`. `map-brand` makes two bounded requests to public pages, never to the authenticated feed; `brands` lists saved mappings and `tracks` lists matched artist/title and stored IDs. To attach a known numbered producer code, set `TPV_KARAOKENNERDS_VIDEO_ID`, `TPV_KARAOKENNERDS_TRACK_CODE`, and `TPV_KARAOKENNERDS_CODE_SOURCE` (`host-confirmed` or `creator-catalog`), then run `set-track-code`. It rejects unknown videos and conflicting replacements rather than inventing or silently changing a code. Do not crawl the site's disallowed ArtistMobile paths; use artist names already present in the cached feed.

For a mapped video, set `TPV_KARAOKENNERDS_VIDEO_ID` and the absolute `TPV_YTDLP_EXECUTABLE`, then run `inspect-video` to save yt-dlp's upload and release date fields separately from the feed's `Created` value. The upload date may serve as the explicitly labeled selection fallback when no verified publication date exists; the release date is not a substitute. To download one selected mapped video, also set `TPV_KARAOKENNERDS_BRAND_SLUG` and an existing absolute `TPV_CACHED_VIDEOS_DIR`, then run `download`. Only explicitly selected, uniquely matched videos are eligible; an existing target is left untouched. This operator command does not add the file to the app's library or start a batch.

For a read-only batch preview, set an absolute `TPV_CACHED_VIDEOS_DIR` and provide selected brand slugs or artist names as newline-separated values in `TPV_KARAOKENNERDS_BATCH_BRANDS` and `TPV_KARAOKENNERDS_BATCH_ARTISTS`, then run `node --import tsx scripts/karaokenerds-catalog.ts preview-batch`. It uses the saved snapshot, brand mappings and previously inspected yt-dlp dates. It checks the cached feed for incomplete artist or brand coverage, reports unresolved choices and collisions, and labels upload-based rankings approximate. It makes no network requests and downloads nothing; it is not a host UI or automatic job. The preview assumes the saved snapshot is the available catalog and does not establish the freshness or completeness of the provider's upstream data.

The seeded timestamp conservatively establishes the attempt cooldown. Refresh refuses an uninitialized database, and status or refresh refuses a missing database path; this prevents a typo from silently creating a new active updater. Check status before any later refresh; do not call the feed directly or reset the database to bypass the interval. Failed attempts also consume the interval. An outstanding attempt fails closed until an operator confirms the relevant updater has stopped and explicitly recovers it. Only the production updater may receive the real API credential; staging uses synthetic data and no upstream key. This legacy SQLite operator is for controlled migration/recovery; it is separate from the deployed MySQL search service and is not its scheduler or high-availability coordinator. If its database is lost or restored, reconcile the last upstream attempt time before resuming refreshes.

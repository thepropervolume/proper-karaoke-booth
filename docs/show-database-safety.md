# Show database migrations and snapshot foundation

The current show database uses SQLite `user_version` **7**. Schema 5 added nullable singer IDs, schema 6 added Party Tyme recording identities, and schema 7 retained queued song identities for scoring across shows. Recognizable older shows and standalone backups are checked against their recorded schema before migration. Older snapshots retain their original schema for use with a compatible app version.

Starting with app version 0.10.4, the host saves a verified standalone copy of an existing show before changing its database schema. Look in `show-upgrade-backups` inside the app data folder. The filename identifies the source and target schemas. A SQLite writer reservation keeps show data stable while the copy includes any committed WAL pages. A backup failure stops startup before migration. Fresh and already current databases skip the upgrade backup. Failed migrations roll back, and an in-app restore workflow is still pending. Preserve the pre-upgrade copy if you need to use the show with an older app.

If a show-state save or remote queue transaction fails and its rollback also fails, the application treats the commit outcome as uncertain and blocks further host and guest changes until restart. This prevents stale in-memory state from overwriting a possibly committed update; restart reloads the database. The host must inspect the recovered show and remote requests before continuing.

`src/main/show-snapshots.ts` contains the snapshot and restore-to-new-file primitives. **Back up show…** uses the live Store connection through a host-only bridge and a native save dialog. The host must choose a new destination; existing files and sidecars are refused even if the native dialog offers overwrite confirmation. The main process tracks the picker, backup and cleanup through bounded shutdown, preventing a late picker result from starting work during shutdown. If temporary cleanup fails, the host is told whether the backup was saved and can retry cleanup. `createShowSnapshot` uses [SQLite's online backup API](https://sqlite.org/backup.html) on an open source connection, validates the copy with `integrity_check`, the supported schema and a minimally usable show state, flushes the copy, then publishes it to a new filename without overwriting a pre-existing file. The caller must keep that connection open until the operation finishes and coordinate shutdown and concurrent writes. Publication uses a same-filesystem hard link; filesystems without hard-link support fail rather than falling back to a partial destination. Existing destination SQLite sidecars cause refusal. A cleanup error reports whether publication already succeeded and carries a main-process-only retry handle; a caller must not blindly retry publication when the destination already exists.

`restoreShowSnapshotToNewFile` validates a standalone backup and writes a **new separate database file**. It does not replace the current show, open a host restore dialog, manage the live database's WAL/SHM files, or restart the app. Do not manually copy only a live SQLite database file while it uses WAL: committed data may reside in the WAL. These primitives do not back up source videos, bumper tracks, settings, keybindings, logos or other files, and the database contains private singer and library data. On Windows, snapshot and temporary-file permissions inherit from their destination's parent; choose a suitably private destination.

`src/main/show-selection.ts` is a **disconnected prototype**, not yet a host restore workflow. It stages a validated backup as a new, generated database filename and records its hash and summary for review. Its files inherit the show's directory permissions; the module does not establish Windows ACLs. If staging publishes a file but subsequent validation or temporary cleanup fails, the main-process error identifies the candidate and whether it was published, and may provide a retryable cleanup handle. An offline cutover validates the reviewed file and atomically changes a separate SQLite selection record; it preserves the prior database and can select it again. The prototype refuses to select either database while that database has SQLite sidecars; it does not recover or remove them. An interruption after commit is reconciled by reading the selection, not by blindly repeating destructive file operations. Corrupt selection data and missing selected databases fail closed. The caller must hold the application instance lock, stop remote rooms and close the current Store before a cutover; startup must read the selection under that lock before opening a Store. These conditions are not wired or enforced by the current app. The application currently continues to use its existing database path.

This prototype relies on SQLite's synchronous transaction and a filesystem that supports same-volume hard links. The staged file is flushed, but file flushing alone does not guarantee that newly created directory entries survive sudden power loss on all filesystems. File identity is checked around verification and again during cutover, but a same-user process can still race those checks. The selection record does not retain the reviewed digest and cannot detect substitution after cutover before the next Store open; safely binding reviewed bytes to first open, without preventing later legitimate writes and recovery, is an unresolved integration gate. ACLs, third-party filesystem tools and concurrent external changes remain deployment concerns. Review the host's actual database directory and test an offline recovery procedure before exposing this to hosts.

Tests exercise legacy upgrade and rollback, future-schema rejection, rejection of orphaned or duplicated staged and playing requests, a live WAL-backed snapshot and restore to a new file, refusal to overwrite existing files or sidecars, invalid or incomplete backups, simulated backup/restore interruption before publication, retryable cleanup after publication, and termination of a child process immediately before and after a selection commit. They do not establish durability across actual power loss, filesystem failures, concurrent external processes or every Windows filesystem. The host backup workflow is available; an in-app restore workflow remains unfinished.

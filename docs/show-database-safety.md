# Show database migrations and snapshot foundation

The current show database uses SQLite `user_version` **9**. Schema 5 added nullable singer IDs. Schema 6 added Party Tyme recording identities, schema 7 retained queued song identities for points, and schema 8 marks the introduction of host-only holds. Schema 9 records the original paths for new lyric conversions. Booth checks older shows and standalone backups against their original schema before migration. Keep the checked pre-upgrade snapshot for rollback with a compatible app.

Starting with app version 0.10.4, the host saves a verified standalone copy of an existing show before changing its database schema. Look in `show-upgrade-backups` inside the app data folder. The filename identifies the source and target schemas. A SQLite writer reservation keeps show data stable while the copy includes any committed WAL pages. A backup failure stops startup before migration. Fresh and already current databases skip the upgrade backup. Failed migrations roll back. Preserve the pre-upgrade copy if you need to use the show with an older app.

If a show-state save or remote queue transaction fails and its rollback also fails, the application treats the commit outcome as uncertain and blocks further host and guest changes until restart. This prevents stale in-memory state from overwriting a possibly committed update; restart reloads the database. The host must inspect the recovered show and remote requests before continuing.

`src/main/show-snapshots.ts` contains the snapshot and restore-to-new-file primitives. **Back up show…** uses the live Store connection through a host-only bridge and a native save dialog. The host must choose a new destination; existing files and sidecars are refused even if the native dialog offers overwrite confirmation. The main process tracks the picker, backup and cleanup through bounded shutdown, preventing a late picker result from starting work during shutdown. If temporary cleanup fails, the host is told whether the backup was saved and can retry cleanup. `createShowSnapshot` uses [SQLite's online backup API](https://sqlite.org/backup.html) on an open source connection, validates the copy with `integrity_check`, the supported schema and a minimally usable show state, flushes the copy, then publishes it to a new filename without overwriting a pre-existing file. The caller must keep that connection open until the operation finishes and coordinate shutdown and concurrent writes. Publication uses a same-filesystem hard link; filesystems without hard-link support fail rather than falling back to a partial destination. Existing destination SQLite sidecars cause refusal. A cleanup error reports whether publication already succeeded and carries a main-process-only retry handle; a caller must not blindly retry publication when the destination already exists.

## Restore a show in Booth

1. Stop karaoke playback and finish any imports, relinks or backups.
2. Choose **File → Restore Show Backup…** and select a Booth `.sqlite` backup. The app checks its integrity, show state and schema. Supported older schemas are migrated on a private copy.
3. Review the singer, song and request counts. Choose **Restore and Restart** to continue. Cancel is the default.
4. Booth ends remote sessions and saves the latest committed current show to a new file in `show-restore-backups` inside app data. After restart, any interrupted performance in the backup is paused. Launch bumper music is suppressed for this restart. Reopen any remote rooms when ready.

To return to the previous show, restore the corresponding `show-before-restore-….sqlite` file in `show-restore-backups` using the same menu. Keep those backups private. Booth snapshots contain singer records and media references. Source videos, bumper tracks, settings, keybindings and logos require separate backups, especially when moving to another computer. On Windows, the profile's access permissions also apply to its restore backups.

For restore, Booth requires a standalone backup with no associated SQLite sidecars and a supported application schema. A raw copy of a WAL-mode database can omit newer committed data. Use **Back up show…** to export a checked copy. Custom triggers, views and virtual tables are rejected.

`src/main/show-restore.ts` reuses the snapshot and migration primitives. It flushes the prepared standalone copy and checks its digest again at cutover. The host keeps its instance lock through shutdown, fences new work, waits for the remote and playback services, and takes a verified rollback snapshot with the live Store open. After the Store closes, a same-volume rename installs the prepared database at the canonical path. Unexpected companion files cause refusal and remain available for recovery. Restoration uses no persistent pending action that could replay on startup. The separate `src/main/show-selection.ts` named-database switching prototype remains outside the host lifecycle.

Tests cover legacy migration, cancellation, protection of WAL-backed current data, malformed inputs, changed staged files, and refusal when preservation fails or a sidecar remains. A power failure, filesystem corruption, or concurrent changes by other processes can affect on-disk durability. Keep an independent backup of important shows.

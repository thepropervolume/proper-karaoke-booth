# Show database migrations and snapshot foundation

The show database uses SQLite `user_version` 1. On opening an existing unversioned show, the app checks its recognizable table shapes and JSON state, then adds the current baseline tables and version in one transaction. Existing rows are preserved. A failed migration rolls back; a newer schema version, an incompatible table, malformed show JSON, or a missing table in a versioned database stops opening rather than silently replacing the show. The check is not a complete semantic audit of every stored value. Keep a separate backup before an upgrade; there is not yet an automatic pre-migration backup or a host backup menu.

`src/main/show-snapshots.ts` contains **unconnected** backup and restore-to-new-file primitives for future integration. `createShowSnapshot` uses [SQLite's online backup API](https://sqlite.org/backup.html) on an open source connection, validates the copy with `integrity_check`, the supported schema and a minimally usable show state, flushes the copy, then publishes it to a new filename without overwriting a pre-existing file. The caller must keep that connection open until the operation finishes and coordinate shutdown and concurrent writes. Publication uses a same-filesystem hard link; filesystems without hard-link support fail rather than falling back to a partial destination. Existing destination SQLite sidecars cause refusal. A cleanup error reports whether publication already succeeded and carries a main-process-only retry handle; a caller must not blindly retry publication when the destination already exists.

`restoreShowSnapshotToNewFile` validates a standalone backup and writes a **new separate database file**. It does not replace the current show, open a host restore dialog, manage the live database's WAL/SHM files, or restart the app. A later integration needs a controlled offline swap with a retained pre-restore copy, startup recovery for interruption, and protection against concurrent application instances. Do not manually copy only a live SQLite database file while it uses WAL: committed data may reside in the WAL. These primitives do not back up source videos, bumper tracks, settings, keybindings, logos or other files, and the database contains private singer and library data.

Tests exercise legacy upgrade and rollback, future-schema rejection, a live WAL-backed snapshot and restore to a new file, refusal to overwrite existing files or sidecars, invalid or incomplete backups, simulated backup/restore interruption before publication, and retryable cleanup after publication. They do not establish durability across actual power loss, filesystem failures, concurrent external processes or every Windows filesystem. There is no finished backup/restore workflow yet.

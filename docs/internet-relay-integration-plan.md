# Internet queueing integration plan

Internet queueing is not enabled. The unmounted `HostInternetPanel` and `InternetRelayBridge` in `src/remote/` are a UI and type contract only: no bridge is exposed by preload, no connector is installed, and no public tunnel is started. The existing local room has its own host controls and lifecycle. A future internet control must manage a separate relay without stopping the local listener or revoking local guests.

Cloudflare describes [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) as a testing and development feature, not a production service. The public hostname is temporary, and Cloudflare terminates browser TLS and can see guest traffic. The host must be told this before enabling it. A separately operated production relay or named tunnel needs its own deployment, privacy, account, cost, availability and recovery design; the development prototype is not a promise of live-show reliability.

## Host experience and provisioning

1. Present separate Local Network and Internet controls with independent stopped, starting, online, stopping and failed states. Explicit host action starts each mode. Internet availability requires a compatible trusted `cloudflared` executable, private loopback TLS identity, scoped guest authority and a working relay; do not claim availability just because a binary exists.
2. Let the host choose a locally installed executable through a native picker. Verify provenance, expected signature or pinned hash, and a tested supported version; keep the absolute path in the main process and show only a safe filename and verified state. No automatic download, update, PATH-based execution, shell command, inherited tunnel credentials or user Cloudflare configuration. Offer official installation guidance separately; do not assume a preinstalled binary.
3. Generate a short-lived private CA and a server certificate with an IP SAN for `127.0.0.1` using a reviewed, bundled certificate implementation. Bind the origin only to loopback. Pass the CA to the connector as an explicit trust pool; never use disabled TLS verification or install a private system root. Keep the private key in memory where possible, protect any unavoidable temporary files, remove them on all exit paths, and generate new credentials for a new room. This provisioning is not implemented yet.
4. Once the verified connector has announced its exact HTTPS origin, allow a host to create a short-lived invitation with its secret in the URL fragment; erase it from singer browser history after use. Display the link only while the corresponding relay room is active. Keep secrets out of logs, paths, queries, analytics and status broadcasts. A link is shareable admission, not identity verification.

## Authority and failure isolation

- Both modes must use the existing single host `Store` authority and identical approval, rotation and content policies. They must not open a second SQLite writer or overwrite the host's current in-memory show state. The existing LAN provider currently owns its authority internally; refactor ownership before composing it with a relay.
- Issue separate invitation, session and resume credentials per mode and enforce scope on every guest route. Stopping, failing or revoking internet access must invalidate internet credentials while leaving local guests, local requests, playback and the local listener intact. A guest reconnecting on a different mode requires a separately authorized link; matching names do not prove identity.
- Gate all internet routes before opening and synchronously on connector failure, abort, host shutdown or room close. Stop accepting connections and revoke internet credentials even if one cleanup operation fails; keep a retryable recovery handle and never report success while the listener or child remains active. Handle startup/close races and bound quit waits without closing the Store underneath pending work. A restarted process must invalidate stale relay credentials before making a new relay available.
- Isolate the child process from inherited configuration and environment; supervise exit and failures without logging output that might contain URLs or credentials. Windows process containment and crash cleanup need explicit testing. Relay failure must not change the LAN room or local show state.
- Do not trust client-supplied forwarding headers. The existing prototype's shared anonymous rate bucket can throttle a room of singers and cannot resist distributed denial of service. Establish authenticated proxy identity and an abuse-control design before public use. Limit bodies, routes, connections and response sizes and preserve the same Host/Origin, authorization and receipt checks as the reviewed local boundary.

## Required verification

Test a trusted executable and its real command-line flags, loopback certificate validation, startup cancellation, process crash, timeout and failed-cleanup retries. Exercise the actual app with both modes open, guest joins and requests over each, cross-scope credential rejection, missed-response retries, local access during relay failure, individual revocation, app quit and forced termination/restart. Test real iOS and Android devices and venue internet/firewall conditions; disclose outage and relay privacy limits. The present fake-process and loopback tests do not demonstrate any public internet connection.

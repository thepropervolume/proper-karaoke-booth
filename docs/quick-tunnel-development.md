# Temporary internet relay prototype

This is **disconnected development scaffolding**, not a usable internet queue. Nothing starts automatically, installs `cloudflared`, creates an account, downloads software, opens a public tunnel, or alters the LAN listener. It is not wired to the desktop app, singer authority, host controls, or a real connector. No public tunnel has been launched or tested.

The intended temporary option is [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), which provides an ephemeral public HTTPS hostname without an account or domain. Cloudflare describes it as development-only: hostnames change, there is no uptime guarantee, the limit is 200 in-flight requests, and Server-Sent Events are unavailable. The host needs a trusted, manually installed `cloudflared` executable, a running application and connector, and outbound access to Cloudflare on [TCP or UDP port 7844](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/). A relay outage must leave local karaoke and LAN queueing operating independently.

## Prototype boundaries

`startQuickTunnelDev` requires explicit `enabled: true`, a trusted absolute executable path, a local certificate and key with an IP SAN for `127.0.0.1`, an explicit CA file, a guest handler and a failure callback. It creates an HTTPS listener bound only to `127.0.0.1` on an ephemeral port, tests that its certificate verifies against the supplied CA, and launches the supplied executable with a fixed argument list, no shell, isolated empty config, isolated copy of the CA and auto-update disabled. It never uses `--no-tls-verify`. It does not generate certificates or install system trust. The public URL is accepted only from the supervised process's startup announcement and must exactly match one HTTPS `trycloudflare.com` hostname; no routes are enabled until it is bound. Exit, cancellation, failure or explicit stop closes the loopback listener and terminates the connector; cleanup failures are reported. Raw process output is not logged or returned. The official 2026.10.7 Windows x64 executable passed checksum, version and help-flag checks without installation or a tunnel; the combined command and behavior remain untested. See [local executable verification](cloudflared-local-verification.md).

The loopback gate requires the exact public Host, requires exact Origin for API POSTs, permits absent Origin for top-level GET navigation, rejects URL query strings and limits routes, connections, request size, and request rates. It does **not** trust forwarded client-IP headers. The rate limits are global and bearer-token based because all relay traffic arrives over loopback; they are basic abuse bounds rather than a substitute for edge protection. The injected handler must independently enforce guest authentication, authorization, bounded JSON/schema validation, same-origin asset restrictions and durable request receipts. The gate alone cannot supply those controls.

The unconnected `RemoteRelayScope` foundation provides separate invitation, session and resume credentials on the same show authority. Its close blocks access immediately and revokes only its own credentials; the first relay scope after a process restart durably revokes stale relay credentials. LAN credentials and other live relay scopes remain independent. `createRelayGuestHandler` combines the allowlisted singer assets with the same guest-only API parser used by LAN. A completed integration must connect this scope to the connector lifecycle, revoke it on connector failure or room close, and avoid revoking LAN guests or stopping a local show. Neither the public hostname nor a claimed forwarded header is an authentication credential. Never attach host IPC, database, filesystem, media or playback controls. Invitations may be shared in a URL fragment that the singer page immediately erases; session and resume secrets must never appear in paths, query strings or logs. A connector outage should close the gate immediately, report the failure, revoke relay access and require explicit host action to reopen.

Browser TLS terminates at Cloudflare: Cloudflare can see guest requests and credentials. The connection from `cloudflared` to the local gate is separately verified TLS. This is not end-to-end encryption between singer and host. Anyone who knows the temporary public hostname can reach the gate, so authentication and abuse controls remain required. Never instruct singers to bypass browser certificate warnings.

The tests use fake process objects, disposable loopback listeners and the public test-only certificate. They cover explicit opt-in, certificate trust rejection, exact origin and Host checks, URL-query rejection, path restrictions, connector timeout/cancellation/exit and cleanup. A separate loopback HTTPS test exercises the real scoped authority and guest router, including cross-scope denial, durable requests and LAN survival after relay closure. They do **not** prove cloudflared compatibility, real public connectivity, browser trust, end-to-end connector-driven revocation, mobile access, sustained attack resistance, or real outage/restart behavior. Those remain blockers before enabling this prototype.

# Ephemeral loopback TLS identity

`createLoopbackIdentity()` is an unconnected main-process helper for the proposed temporary internet relay. It generates an in-memory, short-lived private CA and a separate server identity for **127.0.0.1**. It does not open a listener, run a connector, install a certificate or modify the operating system's trust store. Internet queueing remains unavailable.

Each invocation uses Node WebCrypto to create fresh ECDSA P-256 key pairs and random certificate serials. The CA private key is non-exportable; it signs one server certificate with an IP subject alternative name, a non-CA constraint and server-authentication usage. The returned values are PEM buffers for the public CA certificate, public server certificate and server private key, plus an expiry time. The default lifetime is 24 hours with five minutes of clock-skew allowance; longer lifetimes are rejected. No identity is reused or saved by this helper. `dispose()` overwrites the returned private-key buffer, and cancellation is checked between asynchronous operations. Garbage-collected JavaScript strings, WebCrypto keys, and copies retained by the TLS implementation cannot be reliably zeroed, so this is best-effort cleanup, not a memory-erasure guarantee.

The caller must keep the identity in the main process, avoid logging it, and dispose of the key buffer only after the TLS server has created its secure context or startup has failed. The existing Quick Tunnel supervisor currently takes a CA **file** path; integration must either accept the public CA buffer directly or securely manage a temporary PEM containing only the public CA certificate. Only the connector should receive that CA file, and it must use certificate verification and the loopback IP as the origin server name. Do not write the CA private key or server private key to disk, install a root in system trust, or disable TLS verification. A private CA file is not a substitute for protecting local process and file permissions. Node's `mode` setting alone does not establish restrictive Windows ACLs.

The public singer connection uses Cloudflare's HTTPS certificate; this private CA authenticates only the connector-to-local-server connection. It does not authenticate singers, isolate relay sessions, protect guest data from Cloudflare, or make a Quick Tunnel suitable for production. **Before integration, schedule the relay to stop or safely renew its identity before `expiresAtMs`**: an already-established TLS connection can continue past certificate expiry. Renewal for a long show, abnormal exit, process crash and clock changes require explicit handling. The [Cloudflare origin documentation](https://developers.cloudflare.com/tunnel/reference/origin-parameters/) describes the private CA pool and origin-server-name settings.

The implementation uses pinned `@peculiar/x509`, `@peculiar/asn1-schema` and `reflect-metadata`; the [library documentation](https://peculiarventures.github.io/x509/docs/installation/) requires the Reflect polyfill to load before X.509 code. Focused tests check the certificate chain and IP SAN, fresh identities, valid and expired TLS, rejection without the right CA or hostname, cancellation, key-buffer disposal, and use with the real loopback gate. An isolated esbuild CommonJS bundle was also exercised with Electron 45 and loopback TLS. It did not start `cloudflared` or test a public tunnel, and Go/cloudflared origin verification and packaging on other platforms remain to be tested.

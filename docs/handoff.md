# Development handoff

Updated 11 November 2026 for development delivery 0.2.0. This is the maintained handoff for the local working copy. The [original handoff](original-development-handoff.txt) is retained verbatim as historical context; where its defaults conflict with the decisions below, these decisions govern. The [product review and work list](feature-review.md) records the broader KaraFun comparison and the remaining work.

The planning Word specification (internal revision 0.3) still states the earlier moderation and media-preservation defaults. Until its revised edition is visually verified and published, the decisions below supersede those conflicting passages.

## Product direction and decisions

- The desktop host is the authority for playback, the durable queue and the current show. A party and a show are the same session. Local hosting must work without internet access. Hosts or venues will eventually pay; singer participation is free. Prices, plans and limits remain undecided. The marketing site and branding guide are separate projects.
- New song requests default to **automatic approval**. The host can choose moderation. This supersedes the original handoff's moderated-by-default decision. Switching modes affects new requests; existing pending requests are not silently approved.
- Hosts should be able to edit artist and title locally and choose **per edit** whether supported embedded file metadata should also be changed. Local-only is the default. No import, rescan or ordinary local edit should implicitly modify source media. If an explicitly requested embedded write fails or is unsupported, report that outcome and retain the local edit. The per-edit choice and embedded write-back are **not yet implemented**; the current edit only changes the local database.
- Preserve the accepted mockups and the original handoff's domain, playback safety, privacy, security and accessibility requirements. The requested work list extends those requirements; it does not turn planned features into implemented features.

## Important remaining boundaries

- Embedded tag reading and the host's per-edit file-write choice are not implemented. The [metadata write-back design](metadata-writeback-design.md) records the default-off choice, fingerprint and crash-recovery requirements. MP3/CDG pairs and single-pair ZIP import now convert through external FFmpeg to managed MP4; the timeline supports seek and elapsed/remaining time. Pitch/tempo, automatic filler scheduling, fades and physical verification remain work. Moved MP4s can be relinked only to a byte-for-byte match; full hashes are checked on start, with quick identity checks on normal resume. Concurrent changes after verification and large-file latency remain limitations. Genre browsing is a placeholder until genre metadata exists.
- Hosts can create a checked show database snapshot via **Back up show…**; the save destination must be new and support hard links. Cleanup failures retain a retry action and report whether publication occurred. The database includes private singer and library-path data; destination permissions are inherited. Videos, settings and other external files need separate backup. The app has no live restore flow. The main process tracks the picker and operation through shutdown. See [show database safety](show-database-safety.md).
- Import hashing runs in a worker, reports individual results and can be cancelled without removing songs already committed. Results are in memory until the next import or app exit. The isolated Windows rehearsal covers playback pause during a deliberately slowed import and shutdown/restart; real large libraries, network drives and Dropbox still require testing. See [import jobs](import-jobs.md).
- Singer-display fullscreen requests are serialized across native window transition events; the saved preference takes effect on the next open and the host toggle affects the current display. A muted Electron rehearsal tests fullscreen, exit, reopen and playback pause on window loss; physical monitor disconnect and macOS window-manager behavior remain unverified.
- Experimental bumper playback uses three app-generated themes and up to five host-selected local audio files. It requires an explicit output and an open singer display, begins only by host action, and stops before karaoke starts. It is not a substitute for physical output, handoff, device-loss and mixer tests; see [bumper playback design](bumper-playback-design.md).
- Shared user profiles, the full Host/Co-host/Moderator/Singer/Audience permission model, companions, the CLI, a general-purpose local API, paid karaoke-provider integrations and billing are not implemented. The existing domain roles are a foundation, not a complete access-control system. Do not add a second authority or direct CLI database writer.
- Paid karaoke-provider integration is a high priority, including linking existing eligible KaraFun subscriptions. KaraFun advertises account login and user-linked subscription entitlements for [OEM partners](https://business.karafun.com/oem); no partnership, playback access or specific subscription, commercial, geographic or platform eligibility has been confirmed. The owner supplied a Business management token and OpenAPI document; read-only device and room-token listings returned 402 and 403 respectively. These credentials are not verified content/playback access. See the [Business API findings](karafun-business-api.md); the owner's OEM inquiry is pending. Investigate Party Tyme, Sunfly and Stingray in parallel; see [provider research](provider-research.md).
- Provider developer groundwork includes fixture-tested Sunfly account and catalog-change inspection and Stingray v1 device-login and catalog-search operators. They require provider-issued credentials, do not run automatically, have not been verified with real accounts, and do not implement streaming, subscriber linking or queue playback. See [Sunfly operator](sunfly-account-status.md) and [Stingray operator](stingray-catalog.md).
- Karaoke Nerds metadata recovery found the original 64,261-record raw snapshot. A dedicated shared MySQL search service is deployed at `https://apps.thepropervolume.com`, with 64,261 valid unique YouTube records searchable, including unmapped brands. Server backup and scratch restore passed. No upstream refresh was made for deployment. Original SQLite cooldown, retirement and verified mapping state were not recovered: lastAttempt/lastSuccess/sqlite_retired_ms are null, and refresh is disabled with no upstream key/gate installed. Never infer freshness or old-updater retirement from snapshot file dates.
- The desktop shared HTTPS client, validated private configuration and Preferences controls are implemented. The client retains at most 100 successful query entries/20 MiB for clearly labeled offline use, scoped to endpoint/credential. Provider and DB keys never enter the renderer. A protected app-data configuration and private C:/tmp backup have been provisioned. Live Windows-to-service HTTPS status and search passed: status returned 64,261 raw/searchable records, and Nada Surf / Amateur returned one result. A new client instance reused that query from the durable cache, marked stale, after a simulated connection failure. This does not establish an actual catalog download or real show hardware behavior. An unconfigured/disabled shared connection uses the legacy local browser; a configured outage reports a failure or eligible offline query cache, not a silent database switch.
- Hosts add central results into their local Song Library and use individual yt-dlp downloads and normal singer selection/queue/playback. Singers do not query the central catalog directly. Unmapped brand slugs remain empty and do not become guessed cache paths. Automatic brand/artist batches remain work. Publication/upload provenance remains explicit; feed Created is not a publication date. See [catalog operations](karaokenerds-catalog.md).
- Hosts can reject pending requests and see the 50 most recent terminal request statuses in **Requests**. Authenticated local singers can withdraw their own pending or accepted requests; staged and playing requests remain locked. Guest commands use durable receipts and derive singer identity from the session. Historical request records are retained in show state.
- The host library searches title, artist, filename, DJ code and track number, with sort and metadata/rating filters. Filename lookup returns basenames only to the host; large-library performance remains unverified. In **Requests**, hosts can track unavailable songs through Pending, Reviewing, Fulfilled and Declined; these statuses are private to the host and do not add a song to the rotation.
- The Remote Queueing Preferences panel can explicitly open a local singer room; it is off by default, requires separately provisioned trusted TLS and DNS, and does not offer internet access. A loopback-only Electron/Chromium rehearsal covers opt-in, requests, revocation and shutdown; physical phone trust, venue DNS/firewall and network-failure tests remain open. See [remote host controls](remote-host-controls.md).
- Hosts can promote one eligible waiting request ahead of the remaining queue without displacing a staged song. A stopped promoted performance retains its override unless the host has since chosen another promotion; completion, skip, removal, withdrawal or policy exclusion clears the affected override. Assigned rounds remain unchanged.
- Continue to enforce queue invariants: persist before acknowledgment, staged requests remain locked until released or replaced, preparation never starts audio, a completed or explicitly skipped performance consumes one turn exactly once, and stale media callbacks cannot advance a newer performance. Restored playback must not autoplay.
- Before a permanent media-engine choice, verify synchronized CDG, seek reconstruction, pitch/tempo, single-audio ownership, filler transitions, output loss and platform packaging. Device or display recovery must be deliberate. Source MP4 containers can contain unsupported codecs.
- Policy must eventually apply at all discovery and playback boundaries; age-restricted shows exclude uncertain, conflicting and unrated material. Providers require separate licensing and entitlement validation. Avoid silently substituting recordings or bypassing protected playback.

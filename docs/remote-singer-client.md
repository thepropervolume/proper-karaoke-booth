# Remote singer page foundation

The React page in `src/remote/SingerPage.tsx` is served by the experimental opt-in local room and the deployed internet relay. Local room hosting needs a trusted certificate and DNS. Public singer links at `queue.thepropervolume.com/<slug>` use the authenticated outbound desktop relay, with generation-scoped guest admission. The mobile web app at `/app/` reuses SingerClient in Piggyback mode and can own a separate phone show in Full Host mode. See [mobile development](../mobile/README.md) and [deployment](../deploy/queue-relay/README.md). Physical phone and venue-network testing remains open; the host-authority requirements in [remote queue design](remote-queue-design.md) still apply.

The page allows a singer to join by name, browse paginated policy-filtered songs supplied by the authority, request a loaded song, and see their own request statuses. Search is sent as a bounded authenticated query to the host and covers its complete saved, policy- and source-filtered library; additional matching results can be loaded page by page. It does not query every provider’s full catalog. The client retains the query across refreshes and ignores responses for older searches. Internet search requires a relay deployment that accepts the optional query field. It labels a truncated recent request history. It refreshes periodically and offers manual reconnect using an in-memory resume secret. Its missing-song form submits a title and optional artist for the host to review; this does not add the song to the rotation. The authority derives the singer from the authenticated guest and persists the request and receipt atomically.

The `invite` fragment is removed from browser history immediately, and admission, session, and resume secrets stay in page memory and out of URLs. Closing or reloading the page loses access and requires a fresh invitation. A lost join response is retried with the same identity. If a request response is uncertain, the page blocks further requests and checks its original outcome rather than automatically resubmitting. If a catalog revision changes between pages, it refreshes instead of combining stale pages. None of these client checks replaces server authorization or transaction rules.

The fetch adapter permits only same-origin HTTPS, supplies no cross-origin or insecure fallback, sends sessions in the authorization header and does not send cookies. The LAN server enforces Host/Origin validation, rate and body limits, secure hosting headers, invitation/session lifecycle and authorization. An isolated Chromium rehearsal exercises the hosted page with a test certificate; tests do not establish physical browser trust, real network interruption behavior, relay behavior, accessibility on mobile devices, or physical venue Wi-Fi.

`createSingerStaticHandler(buildRoot)` in `src/main/remote-static.ts` is injected into the opt-in HTTPS transport. It reads only the singer entry and its transitive Vite manifest dependencies into a fixed allowlist, rejects query strings on singer/asset routes, and serves `/singer/` and listed assets with a restrictive same-origin CSP, no-store, nosniff and no-referrer headers. It never takes a filesystem path from an HTTP request, and rejects manifest paths that escape the build directory. It does not open a listener, validate a request's Host or establish TLS; the transport validates exact Host before calling it. Top-level browser navigation does not necessarily include an Origin header, whereas API requests retain the stricter Origin check. A fragment invitation remains client-side and is cleared immediately; do not put credentials in request paths, queries or logs.

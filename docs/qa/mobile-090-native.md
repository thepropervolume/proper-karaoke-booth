# Mobile 0.9.0 Native, Discovery and PWA QA

Reviewed on 17 November 2026 against the in-progress local checkout. This is an audit of source, installed dependencies and isolated Windows probes, not a claim that Android/iOS hardware or store distribution passed. Root owns app fixes unless noted below.

## Findings

| ID | Priority | Finding and evidence | Required correction / disposition |
| --- | --- | --- | --- |
| N01 | P1 | iOS's normal scene launch creates `CAPBridgeViewController()` in `mobile/ios/App/App/SceneDelegate.swift:13`. It replaces the storyboard's custom `TPVBridgeViewController`, so `capacitorDidLoad()` in `TPVRoomDiscovery.swift:58` never registers the discovery plugin on that path. | Instantiate `TPVBridgeViewController()` in the scene delegate. This audit agent is applying the isolated fix; native build/runtime verification remains separate. |
| N02 | P1 | `src/mobile/api.ts:14` supplies a 10s connect timeout and 25s read timeout. Installed Capacitor iOS `HttpRequestHandler.swift:204` uses `connectTimeout ?? readTimeout` as the single request timeout. An idle relay poll waits 20s and therefore cannot finish normally on iOS: it repeatedly enters reconnecting and stops its native advertisement. | Use an effective native request timeout longer than the relay's 20s poll, with an outer bounded deadline and cancellation fencing. Root owns this fix. Verify an idle room for at least two full poll intervals on iOS. |
| N03 | P1 | Initial `src/main/mobile-room-beacon.ts:31` uses a Bonjour error callback that only handles response-send callbacks. Installed `bonjour-service/dist/lib/mdns-server.js` never subscribes to its `multicast-dns` emitter's `error`; that emitter raises asynchronous `EACCES`/`EADDRINUSE` bind errors. An isolated no-network construction probe found zero error and warning listeners. The surrounding synchronous try/catch cannot catch those errors. | Replace the wrapper with the public multicast-dns API, register error/warning handlers immediately, retire failed sockets, and test late errors/close/rechecks. This audit agent owns that isolated replacement. |
| N04 | P1 acceptance gate | The native iOS page has Capacitor's `capacitor://localhost` origin. Initial `Player.tsx:44` only sets the IFrame API's `origin` to `location.origin`; it does not supply the HTTP Referer / app identity required for a bundled WebView player. Error 153 is therefore a material native playback risk. This is a configuration inference supported by Google's documentation, not a device reproduction. | Provide a documented native player identity path, such as a tightly scoped HTTPS player document or native WKWebView adapter. Test a real allowed video on iOS. Do not call native streaming verified because a simulator app compiles. |
| N05 | P2 | `src/mobile/discovery.ts:24` returns immediately on a successful native discovery response, including an empty list. Both plugins can return an empty list after discovery failure/permission denial. Same-egress room hints are consequently skipped precisely when native discovery cannot find the desktop, even though the fallback is available. | Merge or fall back to the same-egress result when native discovery yields no valid rooms. Keep the UI distinction: shared internet egress is a hint, not proof of the same Wi-Fi. |
| N06 | P2 | Initial Android discovery has no generation token: its timer at `TPVRoomDiscoveryPlugin.java:45` and resolve callbacks at lines 54–61 operate on the current global `pending`, `rooms`, `busy` and queue. An early failure or a late resolve from an older scan can finish or contaminate a later scan. iOS `netServiceDidResolveAddress` similarly checks only that some scan is pending. | Give each scan an identity and reject late callbacks; cancel its timeout on every finish path. On iOS, also require the resolved service to belong to the current retained service list. A rapid retry/failure native test is required. |
| N07 | P2 | Initial booth/service names are truncated by JavaScript code units / Java characters / Swift characters, rather than the DNS label's UTF-8 byte limit. A name of 60 accented characters or emoji can exceed 63 bytes. Desktop packet encoding or native advertisement can then fail despite a valid booth name. | Derive a UTF-8-safe service label of at most 63 bytes, retaining the full user-facing booth name separately. Include a long Unicode-name test for the desktop encoder and real native advertisement acceptance. |
| N08 | P2 build gate | The mobile preview's `app.json` was removed, but initial `scripts/verify-brand-assets.mjs:70` still reads it as an Expo configuration. The desktop release workflow calls this validator before packaging, so the migration blocks all desktop release platforms until the validator changes. | Root is updating branding generation/verification for Capacitor and the PWA. Re-run the validator and all release rules before the version bump. |
| N09 | Release gate | The workflow deliberately creates a debug Android APK, an unsigned release AAB and an unsigned iOS Simulator app. These are development artifacts, not signed store releases or an installable iPhone IPA. A new ephemeral CI debug keystore can also prevent an in-place Android update from a previous CI APK. | Label artifacts accordingly. Store distribution needs the owner's stable Android signing configuration and Apple team/provisioning. Do not publish these as production installers or promise upgrade continuity. |
| N10 | P1 | In the intermediate HTTPS player bridge, successive `Player.tsx` native iframe URLs changed only their fragment. The iframe was reused, while `youtube-player.js` read its video/channel only once. A mocked Playwright probe with the actual bridge script confirmed that changing from `#video=Video123456` to `#video=NextVideo01` left the initialized video as `Video123456`. | Key the iframe by its performance/channel so each new song creates a fresh document, or explicitly reinitialize on fragment changes. Root owns the Player component. |
| N11 | P1 | The first HTTPS bridge revision sent native Play/Pause commands from an effect keyed only by song ID/generation. Later changes to the `playing` state did not run it. | Move the native command into the playing-state effect. Root corrected this during review; checked in the updated source. Native button/control acceptance still needs the real bridge test. |
| N12 | P2 | At 320–375 CSS-pixel widths, the initial 16:9 inline player's content width produces a height under 200 pixels. YouTube specifies a minimum embedded viewport of 200 by 200 pixels, and controls/lyrics become cramped. | Provide a 200px minimum inline player height on narrow phones, while retaining fullscreen and fitting the viewport. Root owns the stylesheet. |
| N13 | P2 | A direct mDNS replacement initially used only the booth's friendly name as its DNS-SD instance name. Two hosts with the same default name would compete for the same cache identity despite different room URLs. | The replacement now adds a stable room-derived suffix within the 63-byte label. A test confirms that two rooms with the same booth name have distinct instance records. |

## Fix verification in this audit

The audit agent applied N01, N03, N06, N07 and N13 within its assigned files. The desktop beacon uses the public multicast-dns API, explicit records for the approved interface, immediate asynchronous error/warning handling, 30-second trust rechecks, 5-second announcements and a four-responses-per-second per-interface query bound. Closing, disabling, stale profile replies and late socket failures are fenced. Java scan callbacks carry their scan generation and its timeout is removed on finish; Swift rejects old browser/service callbacks and cancels its scan timeout. Both native implementations truncate service names by UTF-8 bytes.

Six behavioral tests in `tests/main/mobile-room-beacon.test.ts` pass. They cover configuration/network gates, actual DNS packet encode/decode, public TXT projection, query bursts, asynchronous bind/send/warning failures, trust loss, stale async completion, Unicode names and same-name room separation. `npm run typecheck` passed after these changes. These are automated source-level results; they do not establish physical multicast discovery or native compilation.

Root added an HTTPS player shim and corrected N11. The shim's message handler checks its parent window, a bounded origin allowlist, a per-performance random channel, and allowlisted player commands; it carries no room or account credentials. This is a sound way to address the original native origin gap, subject to N10 and actual iOS playback verification. Root also added the empty-native-discovery fallback and updated the branding validator on source inspection. Final integrated and native build results belong in the main release/QA record.

## Verified checks and non-findings

- The custom Android plugin is registered before `super.onCreate()`. Installed Capacitor's `BridgeActivity` collects registrations through `bridgeBuilder`, so that order is supported.
- Android currently targets SDK 36 and requests Internet access. The audit did not establish a missing runtime permission at that target; future local-network permission changes must be evaluated against the actual future target and OS.
- iOS declares its Bonjour service and local-network usage description. Those declarations do not prove that permission prompts, denial/recovery or discovery work on a phone.
- Native discovery accepts a bounded HTTPS URL for the fixed queue domain. The JavaScript parser validates the room slug and does not treat discovery as authorization. Joining is explicit and still performs the server lookup/admission flow.
- A local Windows UDP experiment sent a multicast packet with TTL 0, using a selected private interface. Both wildcard-bound and private-unicast-bound receivers got exactly one packet. Binding directly to the multicast group address failed with `EADDRNOTAVAIL`. Private-unicast binding is therefore **not a confirmed Windows bug** and should be retained until other OS behavior is measured. No external-host probe or firewall change was performed. Linux/macOS multicast behavior remains unverified.
- The PWA service worker's allowlist covers app shell assets only. Queue API responses, bearer tokens, catalog search and provider media are not intentionally cached by that worker. Old/new-worker update and offline behavior still need a browser rehearsal.
- Native HTTP's public address allowlist and `disableRedirects` setting avoid turning the app into an arbitrary URL proxy. Installed iOS Capacitor does normalize Content-Type header casing correctly; lowercased `Headers` output is not an identified JSON-body bug.

## Evidence and required native acceptance

The source findings above were checked against the actual checked-out implementation and Capacitor 8.6.2 dependency source. Native build jobs must establish Java/Gradle and Swift/Xcode compilation; no local Android SDK or Xcode is installed in this Windows session. Hardware acceptance remains: real iPhone/Android local-network permission allow/deny/retry; desktop-to-phone and phone-to-phone discovery; network change/hotspot/isolation; idle polling and app suspend/resume; YouTube playback with correct identity; local video codec/audio/fullscreen; and installed icon / upgrade behavior.

Google documents both the identification requirement and supported native techniques in [API Client Identity and Credentials](https://developers.google.com/youtube/terms/required-minimum-functionality#api-client-identity-and-credentials). Its [IFrame API reference](https://developers.google.com/youtube/iframe_api_reference) defines error 153. These sources support N04's inference; they do not replace a TPV device test.

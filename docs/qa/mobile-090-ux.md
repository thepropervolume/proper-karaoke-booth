# Mobile 0.9.0 usability and playback review

Reviewed on 17 November 2026 against the initial uncommitted mobile implementation after desktop commit `3f0fffa`. This is an independent QA report, not a claim that a phone installation, production deployment or paid-provider stream passed. Root is implementing fixes concurrently; findings describe the reproduced draft unless a later verification is recorded.

## Method and evidence

Used headless installed Google Chrome with Playwright at 320, 390 and 768 CSS-pixel widths, each 844 pixels high. Served the production Vite bundle under a locally intercepted `https://queue.thepropervolume.com/app/` origin. Catalog and nearby-room responses were synthetic. The YouTube player was a small test double that emitted documented player events; no actual YouTube playback, real account, credentials or provider media were used.

Ignored local evidence is under `release/mobile-ux-qa/`: `audit.mjs`, `results.json`, `host-320.png`, `host-390.png`, `host-768.png`, `edge-cases.mjs` and `edge-results.json`. These are reproducible QA artifacts, not distributed product files. The tests deliberately blocked service workers to isolate UI behavior. Initial captured bundle: `assets/index-CsAgtoRP.js`.

Priority: P1 risks data loss or breaks an ordinary playback flow; P2 blocks an accessible or recoverable workflow; P3 is a usability improvement or a smaller limitation. Source-review findings are explicitly distinguished from browser reproductions.

## Findings

| ID | Priority | Type | Finding and evidence | Recommended change / current follow-up |
| --- | --- | --- | --- | --- |
| M-UX-001 | P1 | Bug | **Built-in player controls and host transport disagree.** In all three viewports: queue Wonderwall, press the host Play button, press host Pause, then press the player's own Play control. The outer button still reads **Play**, because `Player.tsx` initially handled only YouTube ended events and had no local-video play/pause handlers. Manual embedded playback therefore also leaves the parent's automatic-advance flag false. | Propagate both play and pause events from every player to the host state, and test blocked-autoplay recovery followed by a manual player tap. Root has added event propagation in source; the captured original bundle predates that fix. Also keep native-player volume changes consistent with the host volume control where the platform exposes them. |
| M-UX-002 | P2 | Accessibility bug | **The queue dialog is not modal for keyboard users.** Its initial focus correctly enters Singer, but Tab advances Cancel → Add Song → BODY → Home → Switch Mode. Escape does nothing, and Cancel returns focus to BODY. Reproduced at all three widths. Initial owning code: `App.tsx` queue dialog rendering, around line 161. | Trap focus, make background content inert, support Escape, restore the initiating queue button, and retain a visible focus ring. Root is implementing these changes. |
| M-UX-003 | P1 | Data-loss bug | **A settings edit can overwrite a newer queue snapshot.** `App.tsx` passes `{ ...state, setting: value }` to `MobileShow.settings`. The initial implementation spread that runtime object over current authority state; the TypeScript `Pick` did not strip extra properties. A concurrent singer request could therefore be replaced by stale UI queue/history data when changing volume, booth name, gap or automatic advance. Source review; this was not a network timing test. Initial owner: `show.ts` `settings`, around line 85. | Copy only the four supported settings fields. Root has made this explicit in source; verify with a stale-input regression test. |
| M-UX-004 | P1 | Data-loss bug | **Continue Without Restoring destroys the data it says was preserved.** Browser test seeded `show/active` with `{format:99, ownerNote:'original-invalid-do-not-overwrite'}`. The page said the original was preserved. Continue Without Restoring → Full Host → favorite Wonderwall wrote a fresh format-1 show to that same key, removing the original. Owners: `App.tsx` `MobileEntry`, initially around line 168; `storage.ts` `saveMobileShow`, line 18. | Preserve the original in a separate recovery record before enabling new writes, provide an export path, or keep the recovery session unsaved until the host explicitly replaces the old show. |
| M-UX-005 | P1 | Data-loss bug | **Two tabs silently replace each other's saved show.** Open both tabs before making edits. Favorite Wonderwall in tab A, then queue it in tab B. IndexedDB ends with `favorites: []` and one queue item: A's saved favorite was lost. Each `MobileEntry` loads an independent `MobileShow`, and both serialize complete snapshots to the same `active` key. Reproduced using two pages in one browser context. | Enforce a single active host writer with a Web Lock and a visible read-only/Take Over state, or use an atomic revision conflict check. Whole-snapshot merging would not safely resolve active performances. |
| M-UX-006 | P2 | Bug | **A dismissed room returns on the next discovery poll.** Dismiss `oasis-night`: zero prompts remain. At the next normal 30-second scan it returns. The reproduction accelerated only this interval to 100 ms and observed 0 → 1 prompts. Owner: `App.tsx` discovery effect, initially around line 45, and the Dismiss callback. | Remember dismissed room identities/generations for the session, with an explicit Find Rooms/refresh action. Do not repeatedly interrupt a host who already declined a room. |
| M-UX-007 | P2 | Import bug | **Import limits and partial failures are not explained.** Source review: `Array.from(files).slice(0, 20)` silently ignores additional selections. A failure after earlier files were saved exits the loop, reports only the error, and provides no per-file or partial-success result. Owner: `App.tsx` `importFiles`, initially around line 99. | Explain the 20-file limit before/after selection, count skipped files, and report imported/failed/unsupported results. Keep successful imports when later files fail, but make that outcome clear. |
| M-UX-008 | P2 | Missing recovery feature | **Local media has no storage-management or deletion path.** The app persists potentially large video blobs but offers no way to remove one, show storage usage, or recover selectively from quota exhaustion. Browser-wide data deletion also removes show history and favorites. Source review of `App.tsx` and `storage.ts`. | Add per-file removal with queued/current-use protection, estimated storage usage, and a confirmed Clear Downloads action that preserves metadata/history when requested. |
| M-UX-009 | P2 | Recovery bug | **Re-importing a missing local video cannot repair its queued recording.** `Player.tsx` tells the host to import the file again, but `App.tsx` always assigns a new UUID on import. The existing queue item continues referring to the missing blob ID. Source review; no real device storage eviction was induced. | Provide Relink for the existing song ID. At minimum, give the complete remove-request → re-import → requeue recovery instructions instead of implying that import alone repairs the request. |
| M-UX-010 | P2 | Usability improvement | **Switch Mode hides an active host room without showing its status.** `Switch Mode` moves to the chooser and unmounts playback, while the `MobileHostedRoom` object remains running. The chooser has no active-room indicator or Close Room action; singers may still be submitting requests to a room the host can no longer see. Source review. | Show the active host room on the chooser, with Return to Host and Close Room. Explain whether switching to another room will close this one. |
| M-UX-011 | P3 | Usability improvement | **Successful action notices use a large permanent portion of a phone screen.** The captured 390px view has a roughly 75px Added to queue banner above the player. With the always-visible transport, this leaves only the beginning of one search result visible without scrolling. The banner persists until dismissed. | Auto-dismiss routine success messages, keep errors persistent, and use a compact live region. Retain the option to review important outcomes. |
| M-UX-012 | P3 | Usability improvement | **The Room tab is offscreen without a strong scroll affordance.** At 390px, Songs/Queue/Favorites/History are visible and Room is beyond the horizontal tab viewport. Users needing the room link must discover sideways scrolling. Browser screenshot evidence. | Add a subtle trailing scroll hint, shorten labels/use a bottom navigation treatment, or make Room/Invite a persistent action. Preserve at least 44px touch targets. |
| M-UX-013 | P3 | Compatibility bug | **Fullscreen can silently do nothing where the element API is absent.** `container.current?.requestFullscreen?.()` skips the call when unsupported; the `.catch` fallback never runs in that case. Source review; actual iOS/WKWebView availability was not tested. | Check support explicitly and offer an inline fullscreen layout or a clear device-specific fallback. Do not advertise casting or fullscreen as verified from desktop emulation alone. |
| M-UX-014 | P3 | Playback parity gap | **Playback position is not restored across app/mode restarts.** The current request persists, but elapsed time is component state only. Re-entering Host remounts the player and begins the same recording at zero; restarting the app also restores it paused at the beginning. Source review. | Document the current restart behavior. Later persist a bounded last-known position and offer Resume or Start Over after user interaction; never auto-resume audio on launch. |

## Positive coverage

- No horizontal page overflow occurred at 320, 390 or 768px. The persistent transport remained within the viewport. Tested transport buttons were approximately 47–56px wide and 49–51px high, exceeding the 44px minimum.
- Search rows displayed a readable title, artist and concise provider/brand label. Source borders and text identified the provider; meaning was not carried by color alone.
- The queue form allowed an empty singer. The singer input had initial focus and a real label. Queue, favorite, move, remove and transport icon controls had accessible names in the inspected paths.
- Search cancellation checks prevented the inspected effect from committing a reply after cancellation. Errors and notices used alert/status roles. Local media paths and authentication values were not displayed in these host UI fixtures.
- The app did not include quiz screens or quiz actions. The tested chooser clearly separated Full Host and Piggyback modes and did not automatically join a detected room.

## Limits and remaining acceptance work

No actual Android or iOS hardware, screen reader, OS permission prompt, soft keyboard, physical audio output, AirPlay/Chromecast, media-codec matrix or application background suspension was tested. No real streaming playback was verified by the mocked player. Native packaging/discovery and relay security are reviewed by the other specialized QA agents. This report does not establish full KaraFun-mobile feature parity.

After fixes, rerun the modal and embedded-player event tests against a freshly rebuilt bundle, the two IndexedDB data-preservation tests, discovery dismissal, import-limit/partial-failure cases, and real mobile playback with an allowed karaoke recording.

# Remote host controls foundation

The host's Preferences include a Remote Queueing panel and a host-window-only bridge, but remote access is disabled: the main process supplies no provider, and every room action rejects without opening a listener. Neither local nor internet remote queueing is operational. A tested lifecycle foundation can support explicit local opt-in, selected certificate/key, invitations and room closure when a reviewed provider is later integrated. Internet access requires a separate relay.

The narrow bridge guards each operation against the actual host window. `HostRemoteLifecycle` rejects arbitrary renderer-supplied paths, separates certificate and key selection capabilities, validates a proposed room and invitation origin, and attempts connection shutdown and guest revocation even if either fails. An eventual provider must retain paths and key bytes in the main process, return safe filename labels, revalidate the selected live interface at start and clean up any resource if its open operation fails. Never send a key or session secret to the renderer. Admission links are secret: return them only in the direct host response, avoid logs and persistence, and use a fragment on the actual trusted HTTPS origin. The panel keeps a displayed link only in memory, hides it at expiration, on room closure or after revocation, and checks the origin and fragment format before displaying it.

## Lifecycle required before wiring

1. Create a single shared `RemoteQueue` against the host `Store`, install committed guest mutations synchronously into the authoritative host state before broadcasting, and fail closed if publication cannot be completed. Host and guest mutations must never run against separate in-memory snapshots or database writers.
2. Keep the listener off at startup and after a crash. Starting must verify the selected interface still exists, the hostname resolves to that address, certificate/key match, validity and hostname coverage, and that singers' devices actually trust the chain. Do not silently fall back to HTTP or suggest bypassing browser warnings. Certificates, DNS, firewall changes and renewal require an explicit provisioning workflow.
3. Bundle and serve the singer page from the exact same HTTPS origin under a strict content security policy. Assign each open room a fresh non-secret `roomId`, publish status transitions promptly, and invalidate any invitation result for an older room. Wire a host-only invitation response and display or QR workflow without exposing invite fragments in logs, analytics, referrers or network URLs. Confirm that a generated link is accepted on real iOS and Android devices.
4. Implement the provider's coordinated close: stop admitting new traffic, revoke all invitations and guest/resume sessions, stop and drain active connections, and report failure rather than claim success if either revocation or listener shutdown fails. The lifecycle attempts both concurrently and blocks reopening after partial failure. It accepts a provider failure callback and disables the room before cleanup; the provider must call it. App shutdown aborts room startup and guest access immediately, then waits up to five seconds for cleanup. The provider must synchronously gate guest operations on abort, prevent authority creation after abort, and clean up a late listener. If cleanup fails or exceeds the deadline, the app exits without closing the Store underneath pending work; the operating system releases the database. Ensure credentials from an interrupted process are revoked or invalidated before a future room opens. These guarantees need end-to-end provider and crash tests before enabling it.
5. Provide a bounded, current, host-only guest list with stable IDs, duplicate-name disambiguation, per-guest revocation, and refresh/reconnect behavior. Revoking invitations affects new admissions only; already admitted guests remain until revoked or the room closes. Verify the UI does not present stale guests or stale invitations as active.
6. The separate internet relay still needs ownership, deployment, host-to-relay authentication, tenant isolation, secure guest routing, expiry, costs, privacy and outage handling. Relay failure must not interrupt the local host show. Do not label internet access available before end-to-end tests.

Tests of the standalone helper cover interface, host/port and share-link validation; these are UI checks and are never a substitute for main-process authorization, certificate trust, TLS, lifecycle or real-device tests.

# Local API design starting point

The authenticated loopback API and bundled CLI provide reads and Preferences/Keyboard Shortcuts navigation. Version 0.10.6 adds a short queue view and explicit opt-in queue changes with revision checks and original-outcome retries. It delegates to the active host and uses its existing database writer. See the [implemented local control contract](local-control-api.md) for routes, enablement, credentials and limits. The families below describe the broader design.

Before adding general mutation or remote API control: authenticate and authorize every request with revocable scoped credentials; bind to loopback by default; require an explicitly enabled, separately secured TLS mode for LAN; use stable IDs, pagination, structured errors, capabilities and effective settings; publish OpenAPI and event schemas; redact media paths, URLs and credentials; enforce personal-library ownership and content restrictions on both list and direct lookup. Commands need caller-supplied IDs, host epochs, expected revisions and durable original outcomes, including errors. Replay must not repeat a mutation or start playback. Web clients must reconnect to authoritative state and must not automatically replay stale controls.

Planned families: `/v1/capabilities`, `/v1/preferences`, `/v1/parties`, `/v1/users`, `/v1/users/{id}/library`, `/v1/catalog`, `/v1/playback`, `/v1/outputs`, `/v1/providers`, `/v1/policies`, `/v1/commands`, and `/v1/events`. Show and party denote the same entity. These names are proposals, not supported endpoints.
